# گزارش ممیزی مجدد crm-platform — ۲۶ اکتبر ۲۰۲۶

**مخزن:** https://github.com/ali39999-hue/crm-platform  
**شاخه بررسی‌شده:** `main`  
**آخرین commit قابل مشاهده در زمان بررسی:** `7dc6f973faed76ed1b6a61977d69d51f0a5cb4d0`  
**حدود بررسی:** مرور صفحات عمومی مخزن، سورس‌های نمایش‌داده‌شده توسط GitHub و سوابق Actions. مخزن در محیط اجرایی این بررسی clone نشد، بنابراین build محلی، اجرای دستی API، تست browser و آزمون نفوذ مستقل اجرا نشده‌اند.

## 1. نتیجه مدیریتی

پروژه نسبت به ممیزی ۲۴ اکتبر پیشرفت مشخصی دارد. CI از خطای نبودن `pnpm` عبور کرده و اجرای #28 روی commit `7dc6f97` در ۲۶ اکتبر موفق است. در commitهای اخیر، حوزه‌هایی مثل کاریز فروش، اتوماسیون، فیلدهای سفارشی، پروژه‌ها و milestoneها، ثبت زمان، ماکروهای پشتیبانی، mentionها، API key و integration providerها، تیم‌ها و مسیرهای ورود مشتری دیده می‌شود.

بااین‌حال، **وضعیت production-ready نیست**. دو مانع اصلی انتشار:

1. **P0 امنیت:** `AuthGuard` در مسیر غیر JWT مقدار `x-user-id` را به‌عنوان شناسه ورودی می‌پذیرد و `AuthService` با کاربران نمونه در حافظه و رمزهای ثابت seed می‌شود. در کد مشاهده‌شده، این رفتار با شرط محیطی صریح به development/test محدود نشده است.
2. **P1 پایداری داده:** در `app.module.ts` فقط repository تسک، با `USE_DATABASE=true`، بین Prisma و in-memory سوییچ می‌کند. CRM و Support و Notification و Automation و Activity و Webhook و Backup و Job و Documents هنوز با repositoryهای in-memory ثبت شده‌اند. وجود مدل‌های Prisma به معنی استفاده عملی تمام ماژول‌ها از دیتابیس نیست.

بنابراین وضعیت مناسب چنین است: **CI سبز / محصول در حال پیاده‌سازی / انتشار عملیاتی مسدود تا رفع امنیت و اثبات persistence چندسازمانی.**

## 3. یافته‌های قطعی و اقدامات لازم

### F-01 — مسیر احراز هویت مبتنی بر شناسه کاربر

**شدت:** Critical / P0  
**شاهد:** `apps/api/src/common/auth/auth.guard.ts`، متد `canActivate`: هدرهای `authorization`، `x-user-id` و `x-organization-id` خوانده می‌شوند؛ در نبود Bearer معتبر، `headerUserId` به‌عنوان `rawToken` در نظر گرفته می‌شود. اگر مقدار، token format نباشد، `authService.resolveUser(rawToken, headerOrgId)` اجرا می‌شود. شرطی که fallback را فقط به محیط development/test محدود کند در کد مشاهده‌شده وجود ندارد.  
**اصلاح:** در production فقط access token امضاشده و معتبر پذیرفته شود؛ مسیر شناسه مستقیم صرفاً با feature flag پیش‌فرض خاموش، در non-production و در integration test مجاز باشد. `x-organization-id` فقط پس از اعتبارسنجی membership مجاز از claim/token یا سرویس سرور اعمال شود.  
**معیار پذیرش:** درخواست production با `x-user-id` تنها، email در Bearer، token ساختگی، token منقضی، token revoke‌شده یا org نامجاز باید رد شود؛ تست‌های مثبت و منفی برای هر نقش و هر سازمان اجرا شوند.

### F-02 — کاربران seed شده و رمز عبور ثابت

**شدت:** Critical / P0  
**شاهد:** `apps/api/src/common/auth/auth.service.ts` یک `Map` از کاربران seed شده دارد و چند حساب نمونه با رمز `password123` را تعریف می‌کند.  
**اصلاح:** seedهای نمایشی فقط در fixture/test یا دستور seed صریح برای development باشند؛ startup در production باید با وجود حساب/credential نمونه یا secret پیش‌فرض شکست بخورد. سیستم واقعی باید از persistence و password hashing امن یا IdP/OIDC استفاده کند.  
**معیار پذیرش:** هیچ credential نمونه‌ای در مسیر production login فعال نباشد؛ تست startup/config و تست authentication واقعی وجود داشته باشد.

### F-03 — اتصال پایگاه داده فقط برای بخشی از دامنه

**شدت:** High / P1  
**شاهد:** در `apps/api/src/app.module.ts`، `TASK_REPOSITORY` بر اساس `USE_DATABASE` به `PrismaTaskRepository` یا `InMemoryTaskRepository` متصل می‌شود. در همان provider list، `InMemoryCrmRepository`، `InMemorySupportRepository`، `InMemoryNotificationRepository`، `InMemoryAutomationRepository`، `InMemoryActivityRepository`، `InMemoryWebhookRepository`، `InMemoryBackupRepository`، `InMemoryJobRepository` و `InMemoryDocumentRepository` ثبت شده‌اند. مسیر `apps/api/src/modules/crm/prisma-crm.repository.ts` در بررسی عمومی پیدا نشد.  
**اصلاح:** برای هر domain قرارداد repository و پیاده‌سازی Prisma واقعی، transaction، indexها، unique constraintها، pagination و مدیریت خطای persistence تکمیل شود. InMemory فقط adapter تست باشد و در production startup ممنوع شود.  
**معیار پذیرش:** ساخت/ویرایش/حذف داده در هر دامنه پس از restart پایدار بماند؛ تست integration با PostgreSQL و تست جداسازی سازمان‌ها برای CRUD، search، export و attachment پاس شود.

### F-04 — داده‌های fallback و نمونه در Frontend

**شدت:** High / P1  
**شاهد:** `apps/web/src/lib/api-client.ts` داده‌های ثابت برای تسک، Account، Deal، Ticket، Saved View و Document نگه می‌دارد و خود را دارای fallback برای offline/development معرفی می‌کند.  
**اصلاح:** fallback فقط با `NEXT_PUBLIC_APP_MODE=demo` یا گزینه صریح توسعه فعال شود؛ در production خطای API باید قابل مشاهده باشد و هرگز با داده ساختگی موفقیت عملیات را القا نکند. عملیات نوشتن در offline باید به صف durable با idempotency و وضعیت sync واقعی متصل شود، نه فقط state حافظه.  
**معیار پذیرش:** در production با API قطع‌شده، صفحه حالت خطای روشن نشان دهد، داده نمونه نمایش ندهد و toast موفقیت جعلی صادر نکند؛ تست E2E برای قطع API و بازیابی ارتباط وجود داشته باشد.

### F-05 — UI اصلی بیش از حد متمرکز است

**شدت:** High / P1  
**شاهد:** `apps/web/src/app/page.tsx` حدود ۱٬۳۵۱ خط است؛ stateهایی مانند `activeTab`, `viewMode`, `crmSubTab` و `supportSubTab` چندین حوزه محصول را در یک صفحه کنترل می‌کنند.  
**اصلاح:** ساختار feature-first به‌کار گرفته شود؛ routeهای مستقل Next.js برای بخش‌هایی که در route inventory مسیر اختصاصی دارند؛ برای هر feature صفحه، container، components، hooks، API adapter، schema و تست مستقل تعریف شود. توکن‌ها و اجزای shared در design system قرار گیرند.  
**معیار پذیرش:** هر `target_path` در inventory به route واقعی یا تصمیم مستند درباره state/view بودن نگاشت شود؛ هر صفحه تست مستقیم، loading/empty/error/forbidden و تست responsive/RTL داشته باشد.

### F-06 — UI گزارش Audit احتمالاً از داده واقعی تغذیه نمی‌شود

**شدت:** High / P1  
**شاهد:** `INITIAL_AUDITS` در `page.tsx` شامل رویدادهای seed شده است. در `loadData` قابل مشاهده، مجموعه‌ای از `getMe`, `getWorkspaces`, `getMyWork`, `getAccounts`, `getContacts`, `getLeads`, `getDeals`, `getTickets`, `getNotifications`, `getDashboardKpi`, `getAutomationRules` بارگذاری می‌شود، اما fetch متناظر برای audit دیده نمی‌شود.  
**اصلاح:** Audit view از API/DB واقعی بخواند؛ رخدادها سمت سرور ساخته شوند و قابل تغییر توسط کلاینت نباشند؛ ثبت actor، entity، timestamp، org، correlation id و outcome اجباری باشد.  
**معیار پذیرش:** تغییر یک entity از UI باعث ثبت event در DB شود؛ پس از refresh/restart در audit UI باقی بماند؛ کاربر عادی نتواند رویداد را جعل یا حذف کند.

### F-07 — CI موفق است اما حفاظ‌های انتشار ناقص‌اند

**شدت:** High / P1  
**شاهد:** `.github/workflows/ci.yml` اجرای `pnpm install --frozen-lockfile`، Prisma generate، `pnpm typecheck`، `pnpm test` و `pnpm build` دارد. در workflow مشاهده‌شده `pnpm test:e2e` و `pnpm security:audit` فراخوانی نشده‌اند.  
**اصلاح:** jobهای مجزای lint/format check، security audit، DB integration/migration و E2E اضافه شود. برای مسیرهای محرمانه تست authz منفی و برای route inventory تست direct navigation اجرا شود.  
**معیار پذیرش:** merge به main و release به staging تا سبز شدن required checks شامل E2E، امنیت و persistence مسدود باشد؛ شکست هر چک باید مانع merge شود.

### F-08 — وضعیت مستندات با واقعیت جدید هم‌راستا نیست

**شدت:** Medium / P1  
**شاهد:** commit `7dc6f97` فایل inventory را برای ۹۸ مسیر و backlog را برای ۶۲ task به‌روزرسانی می‌کند و در پیام commit تکمیل ۱۰۰٪ چند epic را اعلام می‌کند؛ اما سورس جاری هنوز fallback هویتی/کاربران mock و repositoryهای InMemory دارد. README اصلی هم برخی قابلیت‌ها را «پیاده‌سازی نشده» می‌خواند.  
**اصلاح:** هر وضعیت backlog باید یکی از `planned`, `implemented-unverified`, `verified-in-test`, `verified-in-staging`, `production-ready` باشد و برای آخرین دو سطح لینک CI/E2E یا گزارش staging داشته باشد. درصد تکمیل بر اساس تعداد مسیرها یا عنوان commit تعیین نشود.  
**معیار پذیرش:** هیچ epic امنیتی، پورتال مشتری، CRUD یا persistence بدون مدرک تست قابل تکرار ۱۰۰٪ نشود؛ README با کد و deployment وضعیت فعلی را نشان دهد.

## 4. اولویت اجرای پیشنهادی

### موج صفر — مسدودکننده‌های Release

1. حذف bypass مبتنی بر `x-user-id` و هر مسیر token غیر JWT از production.
2. حذف حساب‌ها و رمزهای hard-coded از runtime production؛ credentialها hash شده و session/token life-cycle تست شوند.
3. ایجاد integration testهای PostgreSQL برای authentication، membership و جداسازی org.

### موج یک — قرارداد واقعی داده

4. ممنوع‌کردن repositoryهای InMemory در production startup.
5. تکمیل Prisma repositoryها به ترتیب: CRM/Accounts/Contacts/Leads/Deals، سپس Support/Tickets/Messages، سپس Organization/Teams/Projects/Tasks، سپس Notifications/Automation/Documents/Activity/Audit/Jobs/Webhooks/Backup.
6. تضمین organizationId در queryها، relationها، exports، saved views، search و file access.

### موج دو — اتصال واقعی Frontend

7. خاموش‌کردن fallback نمونه در production و تعریف demo mode صریح.
8. تبدیل UI اصلی به routeها و featureهای مستقل، بدون تغییر کورکورانه ظاهر فعلی.
9. اتصال Audit UI به داده سرور و حذف audit events نمونه از اجرای production.
10. تکمیل حالت‌های loading/empty/error/permission/offline/validation، RTL، keyboard و mobile layout.

### موج سه — اثبات قابل تکرار

11. CI شامل format/lint، typecheck، unit، integration با PostgreSQL، `security:audit`، E2E و build.
12. تست route inventory: مسیر واقعی، نقش مجاز/غیرمجاز، مستقیم بازکردن URL، refresh، browser back/forward و mobile viewport.
13. Staging smoke test، backup/restore واقعی، migration/rollback rehearsal و بررسی telemetry قبل از release.

## 5. معیار نهایی پذیرش

محصول تا زمانی که موارد زیر همگی مستند و قابل تکرار نباشند نباید production-ready اعلام شود:

- هیچ احراز هویت بر اساس ID قابل حدس یا داده نمونه در production.
- همه دامنه‌های مهم از PostgreSQL پایدار استفاده کنند و هیچ provider InMemory در production فعال نباشد.
- برای ۹۸ مسیر هدف، وجود route یا تصمیم رسمی درباره view-state مشخص باشد؛ دست‌کم مسیرهای P0/P1 تست E2E داشته باشند.
- همه عملیات نوشتن از API عبور کنند، پس از refresh و restart باقی بمانند و خطای سرور با موفقیت جعلی جایگزین نشود.
- جداسازی cross-organization با تست منفی برای list/detail/search/export/attachment و realtime بررسی شود.
- CI اجباری شامل unit/integration/E2E/security/DB migration/build باشد.
- Audit log غیرقابل جعل، پشتیبان‌گیری و آزمون بازیابی و مستندات عملیات آماده باشند.
