## ۱. آزمون‌های دود (Smoke Tests) محیط استیجینگ

پیش از انتشار هر نسخه در محیط استیجینگ، این مسیرها باید به صورت خودکار یا دستی بررسی شوند:

1. **بررسی سلامت سرویس (Health Check):**
   ```bash
   curl -f http://staging.internal:4000/api/v1/health
   # انتظار: HTTP 200 با خروجی {"status":"ok","uptime":...,"timestamp":...}
   ```
2. **بررسی گیت‌های پروداکشن (Production Readiness Check):**
   - راه‌اندازی با `USE_DATABASE=true` الزامی است.
   - عدم امکان ورود با رمزهای پیش‌فرض دمو (`password123`) در محیط استیجینگ/پروداکشن.
   - رد قطعی درخواست‌های با هدر `x-user-id` بدون امضای توکن معتبر Bearer JWT.
3. **تست جریان‌های اصلی (Core User Journeys):**
   - ورود کاربر کارمند و مشاهده کارها (`/w/alpha/my-work`)
   - ثبت تسک جدید و جابجایی بین ستون‌های کانبان با اعتبارسنجی ماشین وضعیت دامنه
   - ورود به پورتال مشتریان (`/portal/sign-in`) و تایید عدم نمایش یادداشت‌های محرمانه داخلی (`INTERNAL`)

## ۲. مانور آزمایشی بازیابی از فاجعه (DR Restore Drill Rehearsal)

سیستم مجهز به موتور پشتیبان‌گیری رمزنگاری‌شده با استاندارد نظامی (`BackupService`) است:

1. **الگوریتم رمزنگاری:** AES-256-GCM با بردار اولیه (IV) تصادفی و برچسب احراز اصالت (Auth Tag).
2. **یکپارچگی داده:** تولید چک‌سام هش SHA-256 برای تمام فایل‌های پشتیبان.
3. **مراحل اجرای مانور بازیابی:**
   ```bash
   # ۱. تهیه پشتیبان رمزنگاری‌شده
   curl -X POST http://localhost:4000/api/v1/operations/backup \
     -H "Authorization: Bearer <ADMIN_TOKEN>"

   # ۲. اعتبارسنجی فرآیند بازیابی و چک‌سام
   # سرویس BackupService.restoreFromBackup سلامت هش و رمزگشایی را بررسی و در صورت هرگونه دستکاری متوقف می‌کند.
   ```
4. **تست‌های خودکار:** آزمون‌های `backup.spec.ts` به صورت مستمر فرآیند ایجاد و بازیابی شبیه‌سازی‌شده را تست می‌کنند.

## ۳. اجرای آزمایشی مایگریشن‌های دیتابیس و سناریوی Rollback

1. **تولید و اعمال ایمن مایگریشن:**
   ```bash
   # بررسی وضعیت مایگریشن‌ها
   pnpm --filter @crm/api db:migrate:status

   # اعمال مایگریشن‌های جدید در استیجینگ
   pnpm --filter @crm/api db:migrate:deploy
   ```
2. **طرح بازگشت اضطراری (Rollback Strategy):**
   - قبل از اعمال هرگونه مایگریشن اسکیما، یک اسنپ‌شات کامل از دیتابیس PostgreSQL تهیه می‌شود.
   - در صورت بروز خطای قفل ایندکس یا ناسازگاری داده، تراکنش مایگریشن به صورت اتمیک Rollback شده و اسنپ‌شات قبلی فعال می‌گردد:
     ```bash
     # بازگردانی اسنپ‌شات قبل از مایگریشن در صورت بروز خطا
     pg_restore -U crm_admin -d crm_db_staging backup_pre_migration.dump
     ```

## ۴. پایش، متریک‌های Prometheus و آستانه هشدارها (Observability & SLO Alerts)

1. **اندپوینت شاخص‌ها:**
   - مسیر: `http://staging.internal:4000/api/v1/metrics`
   - استاندارد: خروجی سازگار با Prometheus شامل زمان پاسخگویی (Latency)، کدهای وضعیت HTTP، و مصرف حافظه سرور.
2. **آستانه هشدارهای بحرانی (SLO Alerts):**
   - **نرخ خطای ۵xx:** بیشتر از ۰.۵٪ در بازه ۵ دقیقه‌ای → هشدار بحرانی (Critical P0)
   - **زمان پاسخگویی p95:** بیشتر از ۵۰۰ میلی‌ثانیه برای درخواست‌های عمومی → هشدار هشداردهنده (Warning P1)
   - **نرخ نقض SLA تیکت‌ها:** بیشتر از ۵٪ در گزارش روزانه → ارجاع خودکار به سرپرست پشتیبانی

## ۵. ماتریس تاییدیه گیت‌های انتشار (Release Gates Sign-off)

| شماره گیت | موضوع گیت | وضعیت راستی‌آزمایی | ابزار تایید |
|---|---|---|---|
| **G-01** | رد هدر `x-user-id` در پروداکشن | تایید شده در تست‌های منفی `auth.spec.ts` | AuthGuard + CI |
